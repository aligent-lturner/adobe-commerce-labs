# adobe-commerce-labs

## CI, deployment and recovery

The generated Adobe App Builder workflows remain in `.github/workflows/`: `pr_test.yml` runs for pull requests; `deploy_stage.yml` runs on pushes to `main`; `deploy_prod.yml` runs only for a published, non-prerelease GitHub Release. No workflow uses `pull_request_target`. Adobe's pinned `aio-cli-setup-action@1.3.0` and `aio-apps-action@4.1.0` retain the generated `oauth_sts`, `test`, `build` and `deploy` contracts. Node 24 is used because the installed Commerce SDK requires Node 22–24. The repository check script uses the YAML parser shipped by the installed SDK.

Fork PRs get **no environment**, secrets, OAuth or deploy job. They run `npm ci`, YAML and credential-pattern checks, unit tests, Commerce artifact verification and a credential-free `aio app build` using a non-secret placeholder namespace. A syntax build is not a Stage integration test; if it cannot run without workspace credentials, report failure rather than giving fork code secrets. Same-repository PRs are treated as trusted and may use only `stage` to authenticate `aio app test` using the generated Adobe action. Limit who can push branches in this repository and protect the `stage` environment if same-repository contributors are not trusted. Never run unreviewed contributor code with Stage credentials.

After merge, `main` repeats YAML checks, secret scanning, `npm test`, generated artifact comparison, authenticated `aio app test` and build using `stage`. A distinct job waits for the `stage-deploy` environment reviewer and then deploys to the Stage workspace with the existing Adobe deploy action and `noPublish: true`. A fixed `aio-workspace-stage` concurrency group serializes Stage deployments. `stage-deploy` must be created in GitHub **Settings → Environments**, with required reviewers and the **same Stage workspace secret values and variable names** as `stage`. Set deployment branch restrictions to `main`; configure `stage` to allow only trusted branches. Workflow YAML alone cannot set required reviewers, environment secrets or branch restrictions. Grant `production` required reviewers, separate Production workspace values and an appropriately restricted release policy. Keep Production credentials only in `production`; never in repository-level secrets accessible to PR jobs.

The Stage job uploads only `release-evidence/stage.json` after a successful deploy; the JSON contains the commit, Stage run ID and generated manifest hash, with no `.env`, `.aio`, `workspace.json`, build directory or workspace configuration. Retention is 90 days. Release deployment checks out the tag, requires its commit to be on `main`, looks up a successful Stage `push` run of **that same commit** via GitHub's read-only Actions API, downloads the evidence from that run and compares commit, run ID and manifest hash before invoking any Adobe Production action. The `production` environment approval still applies. Production uses its own `aio-workspace-production` concurrency group. A release without retained, matching Stage evidence must fail closed; restage the **same commit** before retrying. Do not execute Production for a CI dry run.

### Local checks and generated artifacts

Use Node 24 and run `npm ci`, `node scripts/ci-verify.mjs yaml`, `node scripts/ci-verify.mjs secrets`, `npm test`, `npx aio-commerce-lib-app generate all`, `node scripts/ci-verify.mjs generated`, `aio app test` (only after setting up the intended Stage authentication) and `aio app build`. GitHub workflows also require a clean `git diff` for the generated App Management artifacts: commit them with their corresponding `app.commerce.config.ts` change. The custom scanner is a conservative credential-pattern/path check, **not** a replacement for GitHub secret scanning and push protection; enable both in repository settings. Exclude local `.env`, `.aio` and `workspace.json` from commits and artifacts. Never upload the full build tree or use `actions/upload-artifact` with `path: .`.

### Rotation, Stage verification and rollback

Rotate the Adobe OAuth Server-to-Server credential in Developer Console, then update the `CLIENTID`, `CLIENTSECRET`, `TECHNICALACCID`, `TECHNICALACCEMAIL`, `IMSORGID` and `SCOPES` environment secrets for `stage` and `stage-deploy` together; rotate `production` separately. Update the Stage/Production `AIO_RUNTIME_*` and `AIO_PROJECT_*` workspace values from the correct Developer Console workspaces, including `AIO_PROJECT_WORKSPACE_DETAILS_SERVICES`. Do not paste values in PRs, logs or artifacts. Test a trusted PR and a reviewed Stage deployment after rotation, then review a release before Production. If updating action parameters manually, Adobe advises passing **all** parameters in one update call, since omitted parameters are removed.

After Stage deployment, verify the successful `validate` job, reviewed `deploy` job, Stage artifact SHA/manifest digest, App Management installation/upgrade state in Commerce Admin, history permissions and action behavior. Deployment does not run the custom installation step: install the app in Commerce Admin before testing database-backed flows. Validate both success and denied access with your own authorized admin account; keep IMS tokens private. To roll back, stop new releases, identify the last known-good commit with matching successful Stage evidence, restore its source/manifest through a reviewed change to `main`, run the gates and approve the `stage-deploy` job again. A Production rollback requires a new reviewed release for an approved main-branch commit that has its own successful Stage evidence; never bypass the production environment or point its secrets at Stage. Database/schema or encryption-key changes may need a separate data recovery plan; redeploy alone does not undo them.
